# 微信来稿 → 博文

用户在微信里读到、写到的东西，通常是**口语、跳跃、有公众号腔、夹带主观判断**。目标是把它变成他自己博客上一篇读得下去的文章，同时**不能替换掉他的观点**。

过犹不及与原样照搬一样是失败：把口语全部改写成书面腔，文章就没了人味；一字不改地排版，就只是搬运。

## 一、拿到原文

按优先级取内容：

1. 参数里直接给了文本 → 直接用它
2. 参数给了文件名 → 读 `~/blog-v2/inbox/<file>`
3. 参数给了链接 → 抓正文（公众号链接常抓不到，抓不到就请用户复制粘贴，不要编造内容）
4. 用户说「整理收件箱」→ `ls ~/blog-v2/inbox/*.md ~/blog-v2/inbox/*.txt`，逐篇处理，每篇单独确认

原文**必须完整保留**，后面要写进 `drafts/` 的底部归档，成文时对照。

## 二、判断去向（只在真模糊时问）

| 情况 | 去向 |
|---|---|
| 一段感慨、一句观察、配图说说，< 500 字 | `src/content/moments/`（和现有 moment 一个样式） |
| 有明确论点、要论证、> 500 字 | `src/content/posts/` 正式博文 |
| 拿不准 | 问一句「这篇做成 moment 还是正式文章？」 |

## 三、整理规则

**动笔前先读** `C:\Users\26404\.hermes\shared-memory\user-writing-style.md`——他要的成品像他写的，不只是"观点是他的"。

读法：第一层（口语原稿）决定**句子长什么样**，第二层（成文）决定**整篇怎么排**。改完再翻 `~/blog-v2/drafts/_originals/moments-pairs.md` 的对照，确认自己的改写幅度没超过他实际接受过的范围。

### 铁律：零新增

**只能删、拆、调序、改标点，不能新增任何句子。**

- 连接不上就空行分段，不要补「这让……」「于是……」「换句话说……」这类过渡句。
- 不要替他把口语判断升格成书面结论。
- 不要造金句——金句只能是他的原话。

原文意思有缺口、读不通时，**停下来问**，不要自己填。

### 保留的

- 作者的判断、态度、第一人称经验——一个字都不要替他改成中立腔
- **主观限定词原样留**：「我感觉」「我觉得」「挺……的」是他的声音标记，不是要清理的语气词
- 原文的引文、数据、人名、书名，原样保留；原文没给出处的，不要替他补出处
- 原文里的反常识、扎心的表达——那通常正是他想让人记住的部分

### 处理的

- 口水话与重复：删「然后呢」「其实吧」「就是说」这类填充，合并同义反复
- 段落：按**逻辑**分节，不按字数硬切；一节讲一件事
- 小标题只能是**原文里的词**或一个名词短语，不能写成带判断的新句子
- 口语 → 书面：只改到「读起来不别扭」，不改成论文腔
- 标点统一中文全角；引号用「」或 “”，全文一致
- 原文里模糊指代（「这个东西」「那个事」）**优先用原文里已出现的名词还原**；找不到就别猜，问

### 绝不做的

- 不新增事实、数据、案例、过渡句、观点
- 不加「综上所述」「让我们一起」这类总结腔，除非原文本来就有结论
- 不为了结构好看把观点拆散（顺序可以调，但要在改动说明里写清）
- 不写自己的评论

## 四、生成草稿

写到 `~/blog-v2/drafts/YYYY-MM-DD-<slug>.md`（slug 用英文短横线，别用中文），结构：

```markdown
---
title: 标题（用他的话，别造金句）
published: YYYY-MM-DDTHH:MM:SS+08:00
description: 一句话摘要，40 字以内
tags: [标签]
category: 分类（拿不准就留空）
source: 微信
draft: true
---

正文

<details>
<summary>原文</summary>

（完整原文）

</details>

---

## 改动说明

- 删掉了……
- 合并了……
- 结构调整：……（如果动过顺序，写清原来什么顺序、现在什么顺序）
- 存疑：……（原文模糊、可能记错、需要你确认的地方）
```

`published` 用站点时区（`siteConfig.timeZone`，目前是 Asia/Shanghai）的当前时间，不要用机器时区。

## 五、确认与入库

在对话里只给这些，不贴全文：

1. 标题 + 一句话摘要
2. 结构大纲（每节一句话）
3. 字数、原文 → 成文的字数变化
4. 改动说明的要点（3-4 条）
5. 存疑项（如果有）

然后停下等确认。用户说可以之后：

```bash
cd ~/blog-v2
mv drafts/<file>.md src/content/posts/<file>.md     # moment 则移到 src/content/moments/
```

去掉 `draft: true`，把原文归档到 `drafts/_originals/`，跑 `pnpm build` 验证，构建通过再问是否提交。

原文文件从 `inbox/` 移到 `inbox/_done/`。

## 六、配图

微信文章常带图。处理顺序：

1. 原文有图且用户给了文件 → 复制到 `public/assets/posts/<slug>/`，正文用 `/assets/posts/<slug>/xxx.jpg`
2. 只有图没文件 → 明确告诉用户「原文有 N 张图，需要你另存到 …」，正文先留占位注释，别引用不存在的路径（构建会报 404）
3. 没有图 → 不主动加图

## 七、成稿后：更新风格画像

入库之后，回头看一眼这篇和他的既有文章有没有**不一样的地方**，只记变化：

- 他这次的口语化程度比往常高还是低？磨到哪一层他接受了？
- 标题的写法变了没有（判断式 / 名词式 / 问句）？
- 有没有出现新的句式、新的节奏习惯？
- 有没有他否掉的改法（说明口味在往哪边移）？

有变化就追加一条到 `user-writing-style.md` 的「变更日志」，写清**日期 + 观察 + 证据（哪一篇）**；没变化不要写。稳定特征如果被反复推翻，就地修正那一节，并在日志里说明为什么改。

这份画像是活的：它让下一篇比上一篇更贴他。
