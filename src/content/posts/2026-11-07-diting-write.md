昨天写完谛听 0.3 的时候，我以为「写」已经做完了：三栏下面加一个按钮，模型把当天的话扩成一篇网文，读起来顺，字数够，就行了。

今天把它推翻了。

不是界面推翻，是那个功能本身不成立。**如果「写」只是更长、更顺的总结，它就没有存在的理由。** 三栏已经把「看」解决了；一个人没有理由再读一遍同样的话，只是这次分了段、加了形容词。

0.4 换了一个目标：写一篇**只有今天这些原话才能长出来**的短篇。不是复述，是重讲。

![主屏：三栏、今日原话与「让它写」](/images/diting/main-light.png)

## 一、同一批原话，两种用法

三栏和「写」吃的是同一批话，但它们是两套完全不同的活。

三栏求**准**：输出 JSON，短句，不确定就留空；原话里的错字、口误、半句话都保留，因为它是证据。模型只做归类，不做润色。

「写」求**像**：第一人称，「我」是那只伏在脚边的石兽，称用户「你」；底色固定聊斋；开头三句之内必须给钩子；每三百到五百字要有一个新信息；结尾要回响或者反转。它得是一篇小说，不是一封总结信。

这两件事放在同一个按钮下面，很容易互相污染。所以我们给「写」画了一条硬线：

- 人、数字、地点、约定，必须来自当天原话；
- 环境可以写——风声、灯影、血、匣子、红线——但不能变成推动情节的道具；
- 引语只许用原话，可以删，不可以改；
- 不许新增事实。

**允许「讲法」虚构，不允许「事实」虚构。** 这条线是这次返工里唯一没有让步的东西。

## 二、字数不是拍脑袋定的

0.3 的「写」有一个固定字数，结果素材少的时候硬编，素材多的时候又装不下。0.4 改成按去重后的素材字数分五档：

| 当天素材 | 目标字数 |
| --- | --- |
| 少于 600 字 | 700–1300 |
| 600–1500 字 | 900–1500 |
| 1500–3000 字 | 1200–2000 |
| 3000–6000 字 | 1800–2800 |
| 多于 6000 字 | 2500–3500 |

素材少还硬写三千字，必然编；素材多只写八百字，又浪费。分档之后，文章的长度至少和那天的生活有点关系。

代价是实测会超字数 10–20%。上限写进了提示词，模型不总是听。我们接受了这个偏差：故事完整比字数精确重要，但答辩时不能假装它精确。

## 三、开头和手法，都给了选项

同一套提示词写二十篇，会出现二十篇一样的开头。0.4 给了两组选项：

- 开头四选一：从声音、从物件、从一句话、从那天的一个动作；
- 叙事手法四选一：欧·亨利、海明威、契诃夫、鲁迅。

底色固定聊斋。手法可以换，底色不能换；换了，它就从「谛听写的东西」变成「一个 AI 写作工具」。

输出第一行是「篇名：<2–8 字>」，正文不分章。解析器还兼容旧稿的「书名：」「标题：」「第 N 章」；没有章就收成一篇，显示「短篇 · N 字」。模型失败时走兜底稿，阅读页和通知都会标「兜底」——不假装那是它写的。

## 四、80ms 是设计，不是网慢

上一篇文章里我写的是「每 30 毫秒一个字」。那是 0.3，已经作废。0.4 是 **80ms 一个字**。

原因很简单：模型的流式返回比人读得快得多。如果原样刷出来，屏幕会在一瞬间被填满，人来不及读，也来不及感到「它在写」。把每个字压到 80ms，几百字就要几十秒；这几十秒是留给阅读的，不是网络在等。

读者可以点正文，一次显示完；落后太多也会自动加速。正常几百字的内容不会被加速，只有落后太多才追。这个细节写在 `ArticleActivity.java` 的 `PACE_MS` 里，答辩时不要引用旧数字。

## 五、界面从「阅读器」变成「手帐」

0.3 的主屏像一张信息卡片：三栏、按钮、留白。0.4 把它改成一本摊开的纸手帐。

- 顶部两个页签：「记」和「写」。「记」放三栏和今日原话；「写」放当天文章和历史文章。
- 日纸 / 夜纸两套色。日纸是米色纸、暖黑墨、一点朱砂；夜纸是暖黑、灰墨、同一颗朱砂。
- 去掉卡片边框、圆角药丸和第二个强调色。三栏直接压在纸面上，用留白和细线分开。
- 主屏只留一个主按钮「让它写」；朱砂只给这一个按钮。
- 屏幕上那只石兽是 20×18 像素，八个状态分别对应链路的真实状态：记下、别人说话、被否定、书写、写完、断连、被戳、睡着。

![石兽的八个状态](/images/diting/pet-states.png)

## 六、0.4 还多了「声语」

这一版云端多了一个很小的动作：每处理完一段，除了推文字，还推一个声音事件。

- 主人说话被记下：`tick`；
- 说话的是别人、且不是噪声：`hush`；
- 其他情况不发。

板子收到之后直接推 PCM、打开 DAC，功放使能是 GPIO39。声音不是人声，是手机端合成的「石头和木头」：噪声激励加非谐和衰减，三百毫秒以内，不出人声、不成旋律、不用合成器音色。

但板上没有喇叭。要听板子出声，得外接一个 4Ω、1–3W 的喇叭，接 JST PH 1.25 座。演示默认用手机出声；这一点写进了使用手册，免得上台发现「它怎么不响」。

## 七、还没做完的，比做完的多

- 灯语只落地了一部分节律，完整的六态还没跑满；
- 传输仍是明文 TCP，声音只到我们自己的服务器，但不加密；
- 声纹还是单模板折中，阈值 0.48，BGM 和相似人声偶尔会误过；
- 云端是一台 2 核 1.7G 的机器，没有冗余；
- 自动写依赖手机的精确闹钟、通知权限和省电策略，被杀掉就不会写；
- WiFi 名和密码还编译在固件里，换网络要重烧；App 里的「发给板子」是实验入口，填错会掉线；
- 外壳是两片式 3D 打印，104×97.5×44mm，装一节 18650，还不是能日常戴的挂坠。

这些不是「以后再说」的清单，是这一版边界的一部分。答辩时被问到，照实说，比编一个数字安全。

## 八、这次做对的和做错的

做对的：不新增事实的底线；按素材定字数；80ms 的慢读；把「记」和「写」分成两个页签；让石兽的每个状态都能在链路里找到对应。

做错的：0.3 的 30ms 判断；0.4 仍会超字数 10–20%；偶尔把「音频 / 调试」漂移成「匣子 / 红线」；声纹会把 BGM 误收进来；自动写会因手机权限失败。还有，0.3 里那个「逐句否定」的入口被放弃了——它让用户审判每一句话，比逐字稿还累。现在换成更硬的一条：别人的话根本进不了账本。

但「只认主人」也不是绝对安全。它听得见所有人，只是账本里只有你；相似的声音、背景音乐、半句话，仍可能被误记。这是下一版要拿多模板和现场标阈值去补的。

## 补记：别让模型学会你说话的口水词

文章发出去之后，我又回头修了一个很小的 bug。小到差点不配写进来，但它暴露的是同一个问题的另一面。

原话里有很多「嗯」「啊」「那个那个」「就是说」。这是人说话的样子，转录时我们一个字都不改——`original` 是证据，错字、断句、语气词都留着。问题出在下一步：三条提示词都在要求模型「抓原话细节」「尽量用他原话里的词」「引语只许用原话」。模型很听话，把这些词一起学了走。于是右栏、三栏、短篇里开始出现「嗯，那个会又拖到十二点」这种句子——它不是在引用你，它是在模仿你。

修法不是改原话，而是在原话和模型之间加一层派生副本：送模型之前用 `Clean.java` 清一遍，兜底稿也读这份副本。口径是保守的——「嗯 / 啊 / 呃 / 哦 / 那个那个 / 就是说 / 你知道吗 / 对吧」这类删掉；「这个 / 那个 / 然后 / 就是」当指示代词或连词时保留；「金额」「呃逆」「也就是说」「对吧台」这些容易误伤的地方单独保护。原始记录一个字节没动，三栏和短篇拿到的只是它的一份干净投影。

验证也做得很土：一个纯 JVM 的 `CleanCheck`，几十条固定样例，`bash android/check_clean.sh`；再跑一遍整包编译，确认没有把测试类打进 APK。

这件事让我把「证据」和「表达」分得更开了。原话要一字不差地留着，因为它证明那天确实有人说过那句话；但模型读它的时候，不必连咳嗽一起读。
